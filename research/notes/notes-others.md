### UI/UX findings (license FSL: ideas only)
1. Streaming markdown stable-prefix cache. internal/ui/chat/streaming_markdown.go (L1-80 header). While tokens stream, only the trailing part of the document is re-rendered; the "stable prefix" ends after a blank line where no fence/list/table/blockquote is open (fence parity even). Falls back to full render on any doubt. Why: God Eye re-parses the whole message with marked on each delta; long answers will jank. Adopt: in apps/web/src/components/Markdown.tsx, split content at last safe blank line, memoize the HTML of the stable prefix (useMemo keyed on prefix string), re-render only the tail. Effort S. Also add a perf test like their resize_bench_test.
2. One renderer per tool with a shared base. internal/ui/chat/{bash,file,search,fetch,todos,question,diagnostics,mcp,agent,...}.go, all through `baseToolMessageItem` with states pending/ok/error/canceled and a `Compact` mode. Header line = status icon + tool name + one-line param summary; body collapsed with "expand" hint. Why: God Eye has ApprovalCard and generic tool cards; per-tool renderers (todo ratio "3/7" plus the in-progress task name, in todos.go L50-70) read much better. Adopt: a tool-renderer registry in apps/web (Chat.tsx), keyed by tool name. Effort M.
3. Interactive question tool with typed forms. internal/ui/dialog/question_{single,multi,yesno,freetext,confirm,form}.go plus tools/question.go. The agent can ask a structured question (single/multi choice, yes/no, free text) and the UI renders an inline form; answer returns as tool result. Why: God Eye chats show approvals but not agent-asked structured questions. Adopt: new "question" card in ApprovalCard family + server route in chat-routes.ts. Effort M.
4. Plan mode with handoff. internal/agent/templates/plan.md.tpl: plan agent has no edit/bash tools (physically absent), must emit plan between `<!-- CRUSH_PLAN_START -->` and `<!-- CRUSH_PLAN_READY -->` markers; UI (dialog/plan_handoff_inline.go) then shows "approve plan to implement". Why: marker protocol is cheap and robust; God Eye can detect plan blocks in Claude Code output (ExitPlanMode) and render a Plan card with Approve/Edit. Effort S-M.
5. Permission prompt has three outcomes: Allow, Allow for session, Deny (dialog/permissions.go L29-31, 64). ### Architecture / prompts
4. Architect/editor split: coders/architect_coder.py L1-48. A strong "architect" model replies with a plan in prose, user confirms "Edit the files?", then a second cheaper "editor" model with its own edit format applies it (`editor_model`, `editor_edit_format`, map_tokens=0, history not carried). Cost accumulates in one `total_cost`. Why: God Eye auto model routing (plan 1.6) and flows (Faz 8): plan with Opus-class, execute with Sonnet/Haiku-class, with an approval click between. Effort M (flows.ts step type "plan then apply").
5. Repo map: repomap.py (867 lines). tree-sitter tags (def/ref) per file (queries in aider/queries), cached by mtime in SQLite (`TAGS_CACHE`), graph of files via networkx MultiDiGraph with edges file-referencing-file weighted by identifiers, PageRank with personalization boosted for files in chat, files mentioned, and identifiers mentioned in the user message (L420-530), then binary search of how many top-ranked tags fit a token budget (`map_tokens`, default 1024, L670-700), renders only the key lines with grep_ast TreeContext. Docs: aider/website/docs/repomap.md. Why: God Eye already indexes (indexer.ts, embedder.ts); a ranked symbol map is a cheap "project overview" to feed personas/prompt enhancer and a visual "important files" list on the project page. Adopt idea in TS using web-tree-sitter or Bun regex tags; Effort L (M if regex-based).
6. Chat history summarization: history.py (143 lines): when history exceeds budget, split at an assistant boundary, summarize the head with a weak model (recursive up to depth), keep tail verbatim; runs in a background thread (base_coder.py `summarize_start` L1002) so the next turn is not blocked. ### What it is, concretely
1. Language (spec/overview.md). The model emits one statement per line, `name = Component(positional, args)`:
   ```
   root = Card([header, chart])
   header = Header("Monthly Revenue", "Last 6 months")
   chart = BarChart(labels, [series])
   labels = ["Jan", "Feb"]
   series = Series("Revenue", [12000, 15000])
   ```
   Hoisting (a name may be used before it is defined) so layout is written first and data last; unresolved name means "not yet", not error. Features: references, streaming, actions (`@ToAssistant("text", context)` sends a follow-up message back to the model, `@OpenUrl`, `@Set/@Reset` state, `@Run` query/mutation), forms with validation rules (required, email, url, numeric, min/max, pattern), incremental editing by sending only changed statements (patch merged by name, `chart = null` deletes), expressions (arithmetic, ternary, member access), built-ins (`@Count @Sum @Avg @Min @Max @Filter @Sort @Round @Each`), reactive `$state` variables that bind to inputs two ways, `Query("tool", args, default)` and `Mutation(...)` that call tools the host provides (function map or MCP client), custom `@Functions` and custom actions per library, structured error reports `{source, code, statementId, message, hint}` to send back to the model for a one-line fix.
2. Streaming. Parser re-runs on every chunk; unclosed brackets/strings are auto-closed so every prefix is a valid page; mistakes drop only the smallest broken piece (spec 2.3, 2.12). Result at stream end equals parse of the full text. `Renderer` props: `response`, `library`, `isStreaming` (form interactions disabled while streaming), `onAction`, `onStateUpdate`, `initialState`, `onParseResult`, `toolProvider`, `onError` (Renderer.tsx L28-75).
3. Component library you control (react-lang/src/library.ts L40-80): `defineComponent({name, props: zodObject, description, component})` and `createLibrary({components, root, componentGroups, ...})`; `library.toSpec()` and `generateSystemPrompt({library, promptOptions})` (lang-core parser/prompt.ts, 794 lines) generate the system prompt FROM the allowed components, so the model can only emit components God Eye registered. `library.extend()` adds/replaces/removes components. Prompt options (spec/prompt.md 4.2): `inlineMode` (prose plus fenced openui-lang code inside normal markdown, the right mode for a coding chat), `editMode`, `toolCalls`, `bindings`, `tools`, `preamble`, `examples`, `additionalRules`. Backward-compat rules for stored UIs (spec 3): add props only at the end, never reorder/remove, new required prop needs a default.
4. Storage format: responses are stored as plain text with `]]>openui:` marker lines (content/context/end, library id@version) so old messages still render later (spec section 4, prompt.md section 7).
5. Built-in library `openuiLibrary` / `openuiChatLibrary` (react-ui/src/genui-lib, about 60 components): Card, Stack, Tabs, Accordion, Steps, Carousel, Modal, Table (column-oriented, paginated, skeleton while loading), EditableTable, ListBlock, EntityList, Tag/Chips, Callout, CodeBlock, MarkDownRenderer, MetricIndicator, Form/Input/Select/Slider/DatePicker/etc., FollowUpBlock (suggested follow-up buttons), OptionCards, Image/Gallery. Charts (react-ui/src/components/Charts, d3-scale/d3-shape/d3-selection based, no recharts): Bar, Line, Area, Pie, Radar, Radial, Scatter, Funnel, Heatmap, CalendarHeatmap, SegmentedBar, plus Mini sparklines (MiniBar/MiniLine/MiniArea). This list is a superset of God Eye's current chart/stats/progress.
6. Theming and dark mode (react-ui/src/components/ThemeProvider): `ThemeProvider` injects `--openui-*` CSS custom properties (colors as oklch strings) under a CSS selector you choose, `mode="light"|"dark"`, `darkTheme` partial overrides merged onto built-in dark tokens, per-chart palettes (`barChartPalette`, `lineChartPalette`, ..., `CHART_PALETTE_KEYS`), `useSystemThemeMode`, portal class so popovers inherit tokens, `display: contents` wrapper. So it can be mapped onto God Eye's own tokens (set `--openui-background` etc. from God Eye CSS vars, or pass a Theme object built from them). Styles are SCSS compiled to plain CSS (`@openuidev/react-ui/index.css`, "layered" variant under `@layer`), independent of Tailwind.
7. Dependencies and size. react-lang itself: deps `@openuidev/lang-core`, `@openuidev/devtools`, `@openuidev/observability`; peers react, react-dom (optional), zod, optional `@modelcontextprotocol/sdk`. react-ui is heavy: radix (16 primitives), @tanstack/react-table, d3 (scale/selection/shape), date-fns, react-day-picker, react-markdown + remark-gfm + remark-emoji + rehype-katex (KaTeX), react-syntax-highlighter (Prism, a second highlighter next to God Eye's Shiki), lucide-react, lodash-es, floating-ui; peers zustand, zod, react-headless. Prebuilt browser bundle README: `openui-bundle.min.js` about 3.2 MB raw / 900 KB gzip (includes React), `openui-styles.css` about 320 KB raw / 35 KB gzip. Not measured by me for a tree-shaken react-lang-only build (guess: tens of KB gz for lang-core + react-lang; the weight is in react-ui).
8. Telemetry (important, read in code): `@openuidev/lang-core` has a `postinstall` script (package.json L56, src/postinstall.ts) that sends an install event to PostHog (telemetry/shared.ts: host is a CloudFront proxy) unless `OPENUI_TELEMETRY_DISABLED=1` or `DO_NOT_TRACK=1`; payload per the disclosure in telemetry/install.ts L1-14: random install ID, salted SHA-256 project ID (derived from git origin or cwd), package/Node/OS/arch/package-manager versions, CI provider category, Docker flag; no names, paths, source, prompts. ### How God Eye renders rich blocks today (read from the repo)

- apps/web/src/components/RichBlocks.tsx (494 lines): hand-made SVG charts (columns, bars, lines, tooltip, legend, data-table toggle), stat tiles, meters. JSON fences, no streaming of partial blocks (half-written block stays plain), no interactivity, no model feedback loop.

### Recommendation: ALONGSIDE, in phases (not a replacement, not just ideas)
Decision: use OpenUI as an additional renderer for a new fence ```openui (and for the reports/"Insight" pages), keep the existing JSON fences and RichBlocks working. Do not replace `RichBlocks` and do not adopt `react-ui` wholesale. Reasons:
1. It fits the shape of God Eye chat: `inlineMode` is literally "prose plus fenced openui-lang code", which is the same mechanism God Eye already uses for ```chart. A new fence language slots into `enhanceCode` in Markdown.tsx with a one-line addition to `RICH_LANGS`.
2. What it adds that RichBlocks lacks: true streaming of partial UI (every prefix is a valid page), 10+ chart types, tables with pagination, tabs/accordion/steps, forms, `@ToAssistant` buttons (a "Explain this" or "Run the fix" button that sends a follow-up prompt into the God Eye session), incremental edits (dashboards that update by patch), error reports that can be fed back to the model, stored-UI backward compatibility rules, conformance tests. That is a lot of design work already done.
3. Model-agnostic and driven by system prompt only, so it works with Claude Code / Codex / Gemini output God Eye merely observes; but it must be TAUGHT to the model: for sessions God Eye starts, inject the generated prompt (`--append-system-prompt` for Claude Code, AGENTS.md/GEMINI.md snippet, or a persona/"report writer" prompt). Plain terminal sessions the user runs alone will not emit it. Guess: generated prompt for a trimmed library is a few thousand tokens; measure with `generateSystemPrompt` before committing. For God Eye's own LLM calls (summaries, reports, insight, enhance), full control, so best first target.
How (concrete, phased):
- Phase 0, spike (S, 0.5 day): in a scratch branch add `@openuidev/react-lang` + `@openuidev/lang-core` + `zod`, build a tiny God Eye library of 8 components with `defineComponent` wrapping EXISTING God Eye pieces: `Stats` (RichBlocks Stats), `Meter`, `Chart` (RichBlocks chart, props: type, labels, series), `Table` (God Eye table styles), `Callout` (ge-callout), `CodeBlock` (lib/highlight), `Mermaid`, `Stack/Card/Tabs`, `Button` with `@ToAssistant`. Render in `RichBlock` for lang `openui` using `<Renderer library response={code} isStreaming>`. Check bundle delta with `vite build` and lazy-load via dynamic import like Mermaid.
- Phase 1 (M): server side `generateSystemPrompt({library: lib.toSpec(), promptOptions:{inlineMode:true, additionalRules:[God Eye tone rules, "no emoji", "use stats for numbers"]}})` in a new `apps/server/src/richprompt.ts`; use it for Insight/Weekly/Briefing generators (briefing.ts, summarizer.ts, insight/), and as an opt-in "rich answers" toggle that appends it to sessions God Eye starts. Because lib.toSpec() must run where the library is defined, share the library definition between web and server by putting only the zod schemas + descriptions in a `packages/` shared module and the React renderers in web (split "definition" from "component": `defineComponent` takes both, so either generate spec.json at build time like the pi example does with `pnpm generate` -> `src/generated/spec.json`, see examples/harnesses/pi/README.md).
- Phase 2 (M): map `--openui-*` tokens to God Eye tokens via `ThemeProvider` only if using react-ui pieces; otherwise our own components already use God Eye tokens (no theming work at all). This is the main argument for writing our own `defineComponent` wrappers instead of importing react-ui: zero extra CSS, zero Prism, zero KaTeX, consistent look, dark mode for free.
- Phase 3 (M): feedback loop: `onError` -> show a small "fix" chip that sends the structured error back as a follow-up (spec 2.12); `onAction` -> God Eye commands (open file, run flow, create task, approve), restricted by an allowlist; store messages as-is (plain text fences are already persisted by God Eye) and keep library `id@version` in the fence info string so old reports keep rendering when components change (follow spec section 3 rules).
- Optional (L): `@openuidev/langchain`/AG-UI not needed. `assistant-ui` bridge not needed. Vue/Svelte not needed.
Risks and costs:
- Prompt cost and reliability: the model must follow a new language; weaker/local models may produce parse errors (the parser drops the broken piece and reports it, so failures degrade to missing blocks, not crashes). Keep the old JSON fences as fallback. Measure error rate per tool.
- Dependency weight: react-ui is large (radix, d3, tanstack table, katex, Prism, lodash). Avoid it, or lazy-load and use only for specific components; react-lang + lang-core alone are small (not measured).
- 0.x churn: react-ui 0.18 with a tight peer range on react-headless; react-lang is 1.x and spec 1.0 has fixtures and compat rules, so depend on react-lang/lang-core and pin exact versions.
- Telemetry in postinstall (see above): disable and verify with a network-blocked install; add an audit test that greps node_modules for the PostHog host. Commercial layer (Thesys Cloud/Gateway, `cloud` prompt mode, observability-cloud) is optional; never enable.
- Security: model-generated actions. `@OpenUrl` must be allowlisted (http/https only, no `javascript:`; I did not find URL validation in lang-core, so wrap it), `@Run`/Query tools must map only to a God Eye allowlist (read-only by default), `@ToAssistant` should require user click (it does; actions are click-driven and form interaction is disabled during streaming). Markdown inside components must go through DOMPurify like today.
- Mismatch: OpenUI libraries are positional-argument based; renaming/reordering props later breaks stored messages (rules in spec section 3). Design the God Eye component props carefully up front.
- Duplicated effort: charts already exist in RichBlocks; wrap them instead of rewriting, add new chart types only when needed (pie, area, scatter, funnel, heatmap are the useful missing ones for cost/limits/test dashboards).
- Alternative considered: Vercel json-render / Thesys C1 JSON (benchmarked in OpenUI README: OpenUI Lang uses 45-67% fewer tokens, e.g. dashboard 1226 vs 2247 tokens) and Cline's whitelisted JSX preview (react-jsx-parser, section 2 #16): JSX preview is simpler (no new language, ~300 lines) but has weaker streaming recovery, no state/actions/queries, no spec. If OpenUI proves too heavy, the JSX-whitelist approach is the fallback; the ```ui fence design is the same either way, so Phase 0 does not lock God Eye in.
Effort summary: spike S; usable in Insight/Reports M; chat-wide opt-in with feedback loop M-L. Impact: high (rich reports and answers, interactive follow-up buttons).
